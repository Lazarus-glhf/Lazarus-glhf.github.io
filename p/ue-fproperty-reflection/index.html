1. 问题从哪里来

设想有这样一套数据驱动的相机系统，由两类对象组成：

  • Rig（示意类名 UMyRig）：一个可以被蓝图继承的 UObject。策划在 Rig 蓝图里添加变量，比如 FOV、bAiming，并在蓝图事件里每帧计算这些变量的值。
  • Node（示意类名 UMyNode 及其子类）：用 C++ 写的节点，负责把某个值写进相机参数。比如一个"浮点节点"可以修改 FOV。

节点上的值不一定是写死的常量，也可以绑定到 Rig 上的某个变量。为此，我们设计一个"值引用"结构体：

UE 用来解决这个矛盾的工具是反射（Reflection），其中的核心角色是 FProperty。下面一步步拆开来看。

2. C++ 为什么做不到"按名字读成员"

2.1 编译之后，名字就消失了

在 C++ 里写：

1

double V = Rig->FOV;

编译器在编译期就把它变成了"地址 + 偏移"，大致相当于：

1

double V = *(double*)((uint8*)Rig + 0x2A8);   // 0x2A8 只是举例

最终的机器码里只剩下数字 0x2A8，字符串 "FOV" 已经不存在了。所以程序运行起来之后，C++ 回答不了这三个问题：

  • 这个对象有没有一个叫 "FOV" 的成员？
  • 它是什么类型？
  • 它的偏移是多少？

你可能会想到 C++ 的 RTTI，比如 dynamic_cast 和虚函数表。但它们只能回答"这个对象是不是某个类"，回答不了"这个类里有哪些成员"。

enum class EDemoType { Bool, Double };

struct FDemoPropInfo
{
	const char* Name;    // 名字
	EDemoType   Type;    // 类型
	size_t      Offset;  // 距对象开头的字节数
};

struct FDemoRig
{
	bool   bAiming;
	double FOV;
};

// 每个类配一张表（UE 里由工具自动生成，这里手写）
static const FDemoPropInfo GDemoRigProps[] = {
	{ "bAiming", EDemoType::Bool,   offsetof(FDemoRig, bAiming) },
	{ "FOV",     EDemoType::Double, offsetof(FDemoRig, FOV)     },
};

// ① 按名字查表
const FDemoPropInfo* FindProp(const char* Name)
{
	for (const FDemoPropInfo& P : GDemoRigProps)
		if (strcmp(P.Name, Name) == 0) return &P;
	return nullptr;
}

// ② 检查类型  ③ 用"地址 + 偏移"读值
bool TryGetDouble(const FDemoRig& Rig, const char* Name, double& Out)
{
	const FDemoPropInfo* P = FindProp(Name);
	if (!P || P->Type != EDemoType::Double) return false;
	Out = *(const double*)((const uint8_t*)&Rig + P->Offset);
	return true;
}

反射读取的本质就是这三步。在 UE 里，它们与下面这些 API 一一对应：

迷你版 UE
表里的一行 FDemoPropInfo FProperty
整张表 UClass（更一般地说是 UStruct）
① FindProp(Name) FindFProperty<FProperty>(Class, Name)
② P->Type == Double CastField<FDoubleProperty>(Property)
③ *(double*)(&Rig + Offset) DoubleProperty->GetPropertyValue_InContainer(&Rig)

2.3 为什么类型信息必不可少

有人可能会问：表里只存名字和偏移，不存类型行不行？

偏移本身就存在表里，与类型无关，查到那一行就能拿到。真正缺的是另外两件事：要读多少字节，以及这些字节该如何解释。

  • bool 占 1 字节，float 占 4 字节，double 占 8 字节。
  • 同样的 8 个字节，当成 double 和当成指针，解读出来是完全不同的东西。

如果变量其实是 bool，却按 double 去读，就会把它后面相邻成员的 7 个字节也一起读进来，得到一个毫无意义的数。如果是写入，还会把相邻成员改坏。

策划完全可能把变量类型从 Float 改成 Integer，也可能绑定了一个同名但类型不同的变量。所以读取之前必须检查类型。

3. UE 的"说明书"：UStruct 与 FProperty

UE 把上面的迷你反射做成了一整套自动化系统，核心是这样一组类：

1
2
3
4

UStruct              ← "拥有一串 FProperty 的东西"，也就是我们说的"表"
 ├ UClass            ← 类的表：UMyRig、BP_MyRig_C …
 ├ UScriptStruct     ← 结构体的表：FVector（X, Y, Z）、FRotator …
 └ UFunction         ← 函数的表：参数和返回值也是 FProperty

表里的每一行是一个 FProperty，可以把它理解成某个成员变量的"身份证"，上面记着：

  • 名字（FName）
  • 类型：由 FProperty 的不同子类来表示，第 5 节会讲
  • 偏移量（Offset_Internal），以及元素大小 ElementSize
  • 一组标记位（PropertyFlags），例如"蓝图可见"、“仅编辑器”
  • 元数据（meta），例如 DisplayName、GetOptions，只在编辑器中存在

每个 UStruct 通过 SuperStruct 指向自己的父类，形成一条继承链。每张表只登记自己新增的属性，不会把父类的属性复制一份。查找时沿着继承链逐级往上找：

  • FindFProperty(Class, Name) 先查本类，找不到再查父类、父类的父类……
  • TFieldIterator<FProperty>(Class) 默认也会把父类的属性一起遍历出来。

FindFProperty 的第一个参数类型是 UStruct*，而不是 UClass*，因为结构体也是一张表，同样可以查。这一点在第 6 节会用到。

4. 表从哪里来：C++ 属性与蓝图变量

4.1 C++ 的 UPROPERTY：由 UHT 生成

在 C++ 编译器看来，UPROPERTY(...) 这个宏几乎什么也不做。真正起作用的是 UHT（Unreal Header Tool）。它在 C++ 编译之前扫描头文件，为每个反射类型生成 .generated.h 和 .gen.cpp 两个文件。

比如某个节点类 UMyNode 里有一个 UPROPERTY(EditAnywhere) FMyFloatRef Value;，UHT 会在 .gen.cpp 中生成类似下面的代码（已删减）：

	nullptr,
	(EPropertyFlags)0x0020080000000001,             // 属性标记
	UECodeGen_Private::EPropertyGenFlags::Struct,   // 类型：结构体
	...,
	STRUCT_OFFSET(UMyNode, Value),                  // 偏移：由编译器算出
	Z_Construct_UScriptStruct_FMyFloatRef,          // 结构体类型（指向哪张表）
	METADATA_PARAMS(...)                            // 元数据
};

这其实就是迷你版里那张手写的表，只不过改成了自动生成：

  • 名字由 UHT 从源码中读出。
  • 偏移由 STRUCT_OFFSET（本质上就是 offsetof）在编译期算出。
  • 类型、标记和元数据，都由 UHT 从 UPROPERTY 的写法中解析出来。

模块加载时，UECodeGen_Private::ConstructUClass(...) 会根据这些静态描述创建 UClass，并为每一项 new 出对应的 FProperty 子类对象，挂到这个类上。

GENERATED_BODY() 则会往类里注入 StaticClass() 等函数，用来取得这张表。

顺便看一眼标记值 0x0020080000000001。最低位 0x1 是 CPF_Edit，对应 EditAnywhere。而表示"蓝图可见"的 0x4（CPF_BlueprintVisible）没有置位，因为这个成员只写了 EditAnywhere，没写 BlueprintReadOnly 或 BlueprintReadWrite。第 5.4 节会用到这个结论。

4.2 蓝图变量：在蓝图编译时生成

在蓝图里加变量，不需要重新编译 C++。那么这个变量的表项和它占用的内存是从哪来的？

答案是：编译蓝图会生成一个新的 UClass。 假设有一个蓝图 BP_MyRig，父类是 UMyRig。编译后会生成一个 UBlueprintGeneratedClass 对象，它是 UClass 的子类，名字叫 BP_MyRig_C，后缀 _C 表示 Class：

1
2
3
4
5
6

UMyRig                  (C++ 的 UClass)
  自己的属性: [C++ 中带 UPROPERTY 的成员…]
        ▲  SuperStruct
        │
BP_MyRig_C              (UBlueprintGeneratedClass)
  自己的属性: [bAiming, FOV]   ← 只登记蓝图里新增的变量

这些变量的内存接在父类后面。 每个 UClass 都记录着自己的对象一共占多少字节（PropertiesSize）。蓝图编译器排布新变量时，会从父类大小的位置开始往后放，同时考虑内存对齐：

1
2
3
4

一个 BP_MyRig_C 对象的内存：
[ UObject 头 | UMyRig 的 C++ 成员 | bAiming | 填充 | FOV ]
0                                ↑ 父类的 PropertiesSize
                                 蓝图变量从这里开始往后排

创建对象时，UE 按 BP_MyRig_C 的总大小分配内存，所以这条"尾巴"是真实存在的。但 C++ 代码里没有任何名字能指向它，只能通过 FProperty 里记录的偏移去访问。这就是节点必须使用反射的根本原因。

4.3 FProperty 的创建时机

场景 由谁、在何时创建
C++ UPROPERTY UHT 生成静态描述数据，模块加载时由 ConstructUClass 创建
在编辑器中编译蓝图 蓝图编译器（Kismet Compiler）为每个变量创建 FProperty，然后计算偏移和类大小（这一步叫 Link）
保存蓝图资产 FProperty 被序列化进 .uasset
打包后的游戏 没有蓝图编译；加载资产时从 .uasset 反序列化出 FProperty，再执行一次 Link

有一个细节对理解后面的缓存设计很关键：在编辑器里重新编译蓝图时，BP_MyRig_C 这个 UClass 对象会被复用，但它的 FProperty 会被销毁后重新创建。 第 8 节会看到如何应对这一点。

5. 表里的一行：FProperty 的类型体系

5.1 类型 = 子类

迷你版用一个枚举表示类型。UE 的做法不同：每种类型对应一个 FProperty 的子类。

FField
 └ FProperty                    名字、偏移、ElementSize、PropertyFlags…
    ├ FBoolProperty             ← 蓝图 Boolean
    ├ FNumericProperty
    │   ├ FFloatProperty        ← C++ float
    │   ├ FDoubleProperty       ← 蓝图 Float（UE5 起实际为 double）、C++ double
    │   ├ FIntProperty / FByteProperty / ...
    ├ FNameProperty / FStrProperty / FTextProperty
    ├ FEnumProperty
    ├ FObjectProperty ...       ← UObject 指针
    ├ FStructProperty           ← 任意结构体：FVector、FRotator、自定义 USTRUCT…
    └ FArrayProperty / FMapProperty / FSetProperty

所以，“这个属性是什么类型"就等于"这个 FProperty 对象实际是哪个子类的实例”。

补充一点历史：UE 4.25 之前，它叫 UProperty，继承自 UObject。后来为了减轻内存和 GC 的负担，改成了不继承 UObject 的 FField 体系。老文章里说的 UProperty，就是今天的 FProperty。

5.2 CastField：FProperty 版的 dynamic_cast 

1

const FBoolProperty* BoolProperty = CastField<FBoolProperty>(Property);

它的语义和 dynamic_cast 一样：类型匹配就返回子类指针，不匹配就返回 nullptr。引擎里的实现很短（见 CoreUObject/Public/UObject/Field.h）：

1
2
3
4
5

template<typename FieldType>
FORCEINLINE FieldType* CastField(FField* Src)
{
	return Src && Src->IsA<FieldType>() ? static_cast<FieldType*>(Src) : nullptr;
}

UE 项目一般会关闭 C++ 的 RTTI，所以引擎自带了一套类型系统：每个 FField 子类都有一个 FFieldClass，IsA 只需比较位标记，速度很快。

UE 里有两套类型转换函数，分别对应两类对象，不要混用：

对象种类 转换函数
UObject（Actor、Rig、Node…） Cast<T>()
FField / FProperty CastField<T>()

有了 CastField，类型检查就很好写了：

1
2
3
4

bool FMyBoolRef::AcceptsType(const FProperty* Property)
{
	return CastField<FBoolProperty>(Property) != nullptr;
}

bool FMyFloatRef::AcceptsType(const FProperty* Property)
{
	return CastField<FDoubleProperty>(Property) || CastField<FFloatProperty>(Property);
}

注意，Float 版本同时接受 double 和 float：

  • 蓝图里的 “Float” 变量，在 UE5 中其实是 8 字节的 double。
  • C++ 成员如果声明为 float，则是 4 字节。

两者字节数不同，读法也不同，所以 TryGet 里要先判断是哪一种，再分别读取。这就是第 2.3 节说的"类型决定怎么读"。

5.3 GetPropertyValue_InContainer：为什么必须先 Cast

基类 FProperty 不知道自己对应的 C++ 类型，所以没法提供一个"带类型的读取函数"。只有子类知道：

  • FDoubleProperty::GetPropertyValue_InContainer 返回 double。
  • FBoolProperty::GetPropertyValue_InContainer 返回 bool。

因此代码顺序一定是：先用 CastField 得到具体的子类，再调用读取函数。

参数里的 Container 指"装着这个属性的那个对象"，这里就是 &Rig。函数内部计算的是：

1

值的地址 = (uint8*)Container + Offset_Internal (+ ElementSize * ArrayIndex，用于 C 风格定长数组)

另外还有一个不带 _InContainer 后缀的 GetPropertyValue(ValuePtr)，它接收的是已经算好的"值地址"。两者别混淆。

为什么要调用 API 读取，而不是自己拿偏移去读？ bool 位域是一个很好的例子。C++ 里常见这样的写法：

1
2

UPROPERTY() uint8 bFoo : 1;
UPROPERTY() uint8 bBar : 1;

这两个 bool 共用同一个字节，各占其中的一个 bit。如果自己写 *(bool*)(&Rig + Offset)，读到的是整个字节，结果就错了。FBoolProperty 内部记录了字节偏移和位掩码，引擎实现如下（见 UnrealType.h）：

1
2
3
4
5

FORCEINLINE bool GetPropertyValue(void const* A) const
{
	uint8* ByteValue = (uint8*)A + ByteOffset;
	return !!(*ByteValue & FieldMask);
}

蓝图的 Boolean 变量独占一个字节，掩码是 0xFF；位域 bool 的掩码只有 1 个 bit。通过 API 读取，调用方完全不用关心这些差异。

5.4 属性标记：PropertyFlags

每个 FProperty 都带着一组 64 位的标记 EPropertyFlags，定义在 ObjectMacros.h 中。UPROPERTY 里的大多数说明符，最终都会变成其中的某一位：

说明符 / 来源 产生的标记
EditAnywhere / EditDefaultsOnly … CPF_Edit
BlueprintReadOnly / BlueprintReadWrite CPF_BlueprintVisible（ReadOnly 额外带 CPF_BlueprintReadOnly）
在蓝图编辑器里添加的变量 天然带有 CPF_BlueprintVisible
写在 #if WITH_EDITORONLY_DATA 中的 UPROPERTY CPF_EditorOnly
改名为 xxx_DEPRECATED 的属性 CPF_Deprecated

借助这些标记，就能决定"哪些变量允许被绑定"：

1
2
3
4
5
6

static bool CanBind(const FProperty* Property)
{
	return Property
		&& Property->HasAnyPropertyFlags(CPF_BlueprintVisible)
		&& !Property->HasAnyPropertyFlags(CPF_EditorOnly | CPF_Deprecated);
}

三个条件分别是：

  • 必须蓝图可见。 只开放那些"有意暴露给蓝图"的变量，C++ 的内部状态不能让策划随意绑定。
  • 不能是 EditorOnly。 这类属性在打包后根本不存在。如果允许绑定，就会出现"编辑器里一切正常，打包版本却悄悄失效"的情况。这是最难排查的一类 bug，所以干脆禁止绑定。
  • 不能是 Deprecated。 已经废弃的属性不应再被使用。

由此可以推出：如果 C++ 的 Rig 里有 UPROPERTY(EditAnywhere) float BaseFOV;，它不会出现在可绑定变量的列表里，因为它没有 CPF_BlueprintVisible。4.1 节里生成代码的标记位也印证了这一点。想让它可以被绑定，加上 BlueprintReadOnly 或 BlueprintReadWrite 即可。节点只读不写，所以两者都行，选哪个取决于你是否希望蓝图也能修改它。

6. 结构体属性：表中有表

如果想让节点支持绑定 Vector 变量，就会遇到一个问题：FVector、FRotator 以及所有自定义 USTRUCT，在表里都是 FStructProperty，只靠 CastField 无法区分。

6.1 比较 Struct 指针

FStructProperty 有一个成员：

1

UScriptStruct* Struct;   // 指向"这个结构体类型"的描述对象

每种 USTRUCT 在整个进程里只有一个 UScriptStruct 对象，所以直接比较指针就行：

1
2
3
4
5

static bool AcceptsType(const FProperty* Property)
{
	const FStructProperty* StructProperty = CastField<FStructProperty>(Property);
	return StructProperty && StructProperty->Struct == TBaseStructure<FVector>::Get();
}
  • FVector、FRotator 这类引擎核心类型，用 TBaseStructure<T>::Get() 取得对应的 UScriptStruct。
  • 自己定义的 USTRUCT，用 FMyStruct::StaticStruct()。

为什么不比较名字？因为名字比较更慢；不同模块里可能存在同名的结构体；结构体也可能被改名。指针在进程中是唯一的，比较一次只需要一条指令。

6.2 结构体也是一张表

回到第 3 节的继承图：UScriptStruct 也是一种 UStruct，所以 FVector 也有自己的表，里面是三个 FDoubleProperty，分别叫 X、Y、Z。这样就能清楚地理解 FStructProperty 的含义：

我在容器里占了一块内存，这块内存的布局，请去查 Struct 指向的那张表。

6.3 读取：ContainerPtrToValuePtr

FStructProperty 要对所有结构体通用，它不知道具体的 C++ 类型，所以没有带类型的 GetPropertyValue_InContainer。正确的做法是：先确认 Struct 匹配，再把地址按目标类型来解释：

1
2
3
4

if (const FStructProperty* StructProperty = CastField<FStructProperty>(Property))
{
	OutValue = *StructProperty->ContainerPtrToValuePtr<FVector>(&Rig);
}

ContainerPtrToValuePtr<T> 只做一件事：算出"Container + 偏移"，然后转成 T*。它不检查类型，所以前面那一步 Struct == 的检查绝对不能省。

还有一个和 float/double 同类的坑：UE5 的 FVector 是 double 版本，而 C++ 里有时会用 FVector3f（float 版本）。它们是两个不同的 UScriptStruct，指针比较不会相等。

理解反射时，最容易出错的地方是"该传哪个地址"。下面用一个两层的例子来说明。

问题：Rig 蓝图里有一个 Vector 变量 Offset，现在只用反射读取 Rig.Offset.Y。

1
2
3
4

6
7

// 第一层：在 Rig 的表里找 Offset，Container = &Rig

	FindFProperty<FProperty>(Rig.GetClass(), TEXT("Offset")));
const void* VecPtr = OffsetProp->ContainerPtrToValuePtr<void>(&Rig);   // = &Rig + 0x300

// 第二层：在 FVector 的表里找 Y，Container = VecPtr

	FindFProperty<FProperty>(OffsetProp->Struct, TEXT("Y")));
double Y = YProp->GetPropertyValue_InContainer(VecPtr);                // = VecPtr + 0x8
读取 属性登记在哪张表 Container

Y FVector 的 UScriptStruct Offset 这个向量的起始地址

一个常见的误解，是把 Container 当成"属性本身的类型"，或者把它和读出来的值混为一谈。Container 是"装着这个属性的那个对象"的起始地址。读出来的 Y 是结果，不是 Container。

7.1 为什么是这样：偏移相对于"自己的表"

每个 FProperty 的偏移，都是相对于它所属的那个 UStruct 的起点计算的：

1
2
3
4
5

Rig 对象内存（示意）：
&Rig + 0x000  [ UObject 头 ... C++ 成员 ... ]
&Rig + 0x300  [ Offset.X ]  ← OffsetProp 的偏移 = 0x300（相对 Rig 起点）
&Rig + 0x308  [ Offset.Y ]  ← YProp 的偏移 = 0x8（相对 FVector 起点！）
&Rig + 0x310  [ Offset.Z ]

YProp 只知道"我在 FVector 的第 8 个字节"，并不知道这个 FVector 放在哪个对象里。所以必须由调用者把那个 FVector 的起始地址交给它。

7.2 传错会怎样

如果第二层错误地传入了 &Rig，读取的地址就成了 &Rig + 0x8。这个位置位于 UObject 头部，读出来的是垃圾数据，而且不会有任何报错。反射 API 并不知道你传进来的地址"是什么"，它只负责做加法。

7.3 记忆规则

属性在哪张表里找到，就把那张表的一个实例的地址作为 Container 传进去。上一层算出的值地址，就是下一层的 Container。

三层嵌套也是一样。例如读取 Rig.Data.Pos.Z，其中 Data 的类型是 FMyData，Pos 的类型是 FVector：

层 查哪张表 Container
1 Rig.GetClass() &Rig
2 FMyData 的 UScriptStruct Data 的地址
3 FVector 的 UScriptStruct Pos 的地址

回到我们的节点：变量是在 Rig.GetClass() 这张表里找到的，所以 TryGet 里传入的 Container 是 &Rig。

8. 运行时：查找与缓存设计

有了前面的基础，就可以完整地看懂运行时的读取路径了。

8.1 调用链：每帧执行 

1
2
3
4
5
6

相机管理器（每帧更新）
 └ Rig->Run(...)
     ├ 蓝图事件：计算变量（FOV、bAiming…）     ① 先写

          Node->Apply(Rig, ...)              ② 后读

这里有两点值得注意：

  • 蓝图先写、节点后读，都在同一帧内完成。 所以节点读到的一定是本帧刚算出的值。
  • TryGet 每帧都会执行，执行次数是"节点数 × Ref 数"。FindFProperty 要沿着属性链表逐个比较名字，找不到还得继续查父类。FName 比较虽然便宜，但每帧都这样遍历仍是浪费，所以需要缓存。

8.2 先弄清所有权：为什么缓存几乎总能命中

在 UE 里，这类"一个宿主对象下挂若干节点"的结构，通常这样声明：

  • 宿主类上的节点数组标记为 Instanced：UPROPERTY(EditAnywhere, Instanced) TArray<TObjectPtr<UMyNode>> Nodes;
  • 节点类本身标记为 DefaultToInstanced, EditInlineNew。

这样一来，每个 Node 都是它所属 Rig 的子对象，Node 的 Outer 就是 Rig。运行时用 NewObject<UMyRig>(Outer, RigClass) 创建 Rig，Instanced 的 Node 也会随这个 Rig 实例各复制一份。

因此在实际运行中，每个 Ref 自始至终只会遇到一个 Rig 类：第一帧查找一次，之后每帧都命中缓存。

8.3 为什么用 GetClass() 而不是 StaticClass() 

1

const UClass* Class = Rig.GetClass();
  • UMyRig::StaticClass() 是静态函数，结果在编译期就已确定，永远返回 C++ 类 UMyRig 的 UClass，与具体是哪个对象无关。
  • Rig.GetClass() 是成员函数，读取的是对象创建时记下的"我属于哪个类"，也就是运行时的真实类型，这里是 BP_MyRig_C。

可以把两者类比为 C++ 中的"静态类型"和"动态类型"。如果误用了 StaticClass()，查找范围只覆盖 C++ 类及其父类，而蓝图变量登记在 BP_MyRig_C 的表里，所以永远查不到。

同样的道理，缓存必须以类作为 key。两个不同的蓝图 BP_RigA_C 和 BP_RigB_C，即使都有名为 FOV 的变量，偏移甚至类型都可能不同。从 A 查到的 FProperty，绝不能拿去读 B。

struct FMyValueRefBase
{
	// ...
protected:
	const FProperty* FindBoundProperty(const UMyRig& Rig) const;

private:
	mutable TWeakObjectPtr<const UClass> CacheOwner;
	mutable const FProperty* CacheProp = nullptr;
#if WITH_EDITORONLY_DATA
	mutable int32 CacheSerial = 0;
#endif

const FProperty* FMyValueRefBase::FindBoundProperty(const UMyRig& Rig) const
{
	const UClass* Class = Rig.GetClass();

	// 1. 缓存命中：同一个类，且（编辑器下）类的属性没有被重建
	bool bHit = CacheOwner.Get() == Class;
#if WITH_EDITORONLY_DATA
	bHit = bHit && CacheSerial == Class->FieldPathSerialNumber;
#endif
	if (bHit)
	{
		return CacheProp;
	}

	// 2. 未命中：先记下"这次查的是哪个类"，再查找
	CacheOwner = Class;
#if WITH_EDITORONLY_DATA
	CacheSerial = Class->FieldPathSerialNumber;
#endif
	const FProperty* Found = FindFProperty<FProperty>(Class, GetBoundName());
	CacheProp = (CanBind(Found) && AcceptsProperty(Found)) ? Found : nullptr;

	if (!CacheProp)
	{
		UE_LOG(LogTemp, Warning, TEXT("Bound variable '%s' is not usable on %s"), ...);
	}
	return CacheProp;
}

下面逐个说明其中的设计点。

const 函数 + mutable 成员。 缓存不会改变"这个 Ref 绑定了什么"这一对外可见的状态，属于逻辑上的 const。这是 C++ 里实现内部缓存的惯用写法。

条件一：类是否相同。 这就是 8.3 节说的以类为 key。

条件二：FieldPathSerialNumber。 这是 UStruct 上一个仅在编辑器中存在的字段（见 Class.h），引擎对它的注释是：

Unique id incremented each time this class properties get destroyed

在 UStruct::DestroyChildPropertiesAndResetPropertyLinks() 中，每次销毁属性都会把它更新为一个新的序号。

结合 4.3 节提到的事实：在编辑器中重新编译蓝图时，UClass 对象被复用，但 FProperty 会被销毁重建。

  • 如果只检查条件一：类指针没变，缓存被判定为有效，但缓存里的 FProperty* 已经指向被释放的内存，结果可能是崩溃，也可能悄悄读到垃圾数据。
  • 加上条件二：序号变了，就说明属性已经重建过，需要重新查找。

打包后的游戏不会重新编译蓝图，所以这个字段和这项检查都放在 WITH_EDITORONLY_DATA 里，运行时没有任何开销。引擎自带的 TFieldPath（见 FieldPath.h）用的也是同一套序号机制，这里相当于手写了一个更轻量的版本。

失败结果也会被缓存。 未命中时，代码先把类记下来，再去查找。所以即使没找到，CacheOwner 也已经设置好了，CacheProp 为 nullptr。下一帧两个条件都满足，直接返回 nullptr。这带来两个好处：

  • 失败后不会每帧重复查找；
  • 不会每帧刷 Warning：每个 Ref 对每个类只警告一次，避免在高频路径上刷屏。

8.5 两种缓存指针的选择

为什么 CacheOwner 用 TWeakObjectPtr，而不用裸指针？

先纠正一个常见误解：UE 的 UObject 不使用引用计数，它的生命周期由垃圾回收（GC）管理。TWeakObjectPtr 也不是什么"不计数的智能指针"，它的作用是：

对象被销毁后，Get() 返回 nullptr。

它内部存的不是地址，而是"对象在全局对象表中的索引 + 序列号"。对象被销毁，或者该索引被其他对象复用时，序列号就对不上了。

如果换成裸指针 const UClass*，会有三个问题：

  1. 它无法让类保持存活。这个 struct 不是 UObject，这个成员也不是 UPROPERTY，GC 根本看不到它。
  2. 类被销毁后，这个裸指针就成了悬空指针。
  3. 最危险的情况是：新的 UClass 恰好被分配到了同一个地址。这时 CacheOwner == Class 会误判为相等，返回一个属于旧类、早已被释放的 FProperty。这就是所谓的 ABA 问题。

缓存本来就不应该延长类的生命周期，所以"弱引用 + 能感知销毁"正合适。客观地说，在 8.2 节的所有权结构下，只要 Rig 实例还在，它的类就一定还在，所以这里更多是一种防御性的写法。

为什么 CacheProp 不能也用 TWeakObjectPtr？ 因为 FProperty 是 FField，不是 UObject（见 5.1 节）。引擎为 FField 提供的对应工具是 TFieldPath。这里选择"裸指针 + 序号检查"这种更轻量的方案：FProperty 的生命周期从属于它所在的类，只要类没变、属性没有重建，裸指针就是安全的。

8.6 读取失败时应该怎么办

TryGet 返回 false 之后，节点该如何处理是一个设计选择。一种比较稳妥的约定是：

Ref 用途 读取失败时 效果
“是否生效"这类开关 保持默认值 true 节点照常工作，不因一个开关读不到就整体失效
要写入的数值 放弃这一项 不修改，保持原值

也就是说，绑定失效时，节点退化为"不修改”。整个过程中，日志里只有查找函数打出的那一条 Warning。

8.7 情景推演：PIE 中删除变量

假设在 PIE 运行中，策划在 BP_MyRig 里删掉了变量 FOV，然后点击编译。如果 Ref 对象在重新编译后仍然存活，过程如下：

  1. 条件一通过（还是同一个类），条件二不通过（属性被重建，序号变了）。
  2. 重新查找时找不到 FOV，打出一条 Warning。
  3. 绑定了 FOV 的节点从此按"不修改"处理，之后的帧不会再打日志。

如果同一个节点上有两个 Ref 都绑定了 FOV，就会各打一条，因为警告是按 Ref 对象计算的。

需要说明的是：删除变量会改变类的内存布局，引擎可能会对现有的 Rig 实例做重实例化，也就是用新对象替换旧对象。这时新 Node 里的缓存是空的，条件一会先不满足。具体走哪条路径取决于引擎的编译流程，但最终结果相同：重新查找、打一次 Warning、不修改。序号检查要防的，正是 Ref 对象跨越重新编译而存活下来的那种情况。

  2. 判断这个结构体是不是一个 Ref。 这里用的是 IsChildOf，而不是第 6 节的指针 ==，因为 FMyFloatRef、FMyBoolRef 都是 FMyValueRefBase 的子结构体。UScriptStruct 同样通过 SuperStruct 记录继承关系，它和 UClass 一样都是 UStruct。
  3. Container 是 this，也就是 Node。 属性是在 Node 的表里找到的，自然要传 Node 的地址，这正是第 7 节的规则。拿到的地址被当作基类引用使用。那块内存里确实是一个完整的 FMyFloatRef，带有虚函数表，所以调用 GetBoundName() 这样的虚函数时，会正确分派到子类的实现。

这样设计的好处：以后新写的 Node 子类只要声明 UPROPERTY() FMyFloatRef Xxx;，刷新绑定、数据校验等逻辑就会自动覆盖到这个字段，不需要手动登记。

它的限制：只能找到顶层的 Ref。比如：

这一行在表里是 FArrayProperty，不是 FStructProperty，所以 TFieldIterator<FStructProperty> 会直接跳过它。数组元素的类型记录在 FArrayProperty::Inner 里，迭代器不会深入进去。

注意，这里的判断和"蓝图是否可读"无关。遍历 Ref 时并不检查属性标记；CanBind 检查的是 Rig 那张表里的变量。这是两张表、两个不同的反射对象，不要混为一谈。

它的工作过程如下：

  1. 细节面板发现 BoundName 带有 GetOptions 元数据，于是用下拉框控件来绘制它（见 PropertyEditor 模块中的 SPropertyEditorCombo）。
  2. 下拉框需要选项时，引擎的 PropertyEditorUtils::GetPropertyOptions 会通过 PropertyPathHelpers::GetPropertyValue，在被编辑的对象（Node）上按名字反射查找并调用这个函数。
  3. 函数返回的名字列表，就成了下拉框的选项。

UFunction 也是 UStruct 体系的一员（第 3 节），所以"按名字找函数"和"按名字找属性"是同一个思路。由此可以得出两个结论：

  • 函数必须写 UFUNCTION()，否则它不会出现在表里，细节面板找不到它。
  • 函数可以是 private 的。C++ 的访问控制只在编译期生效，反射调用不受它约束。

如果忘了写 UFUNCTION()，会发生什么？ 查看引擎源码后可以确定：

  • 能编译通过。 meta 只是一个字符串，UHT 不会检查这个函数是否存在。
  • 细节面板仍然显示下拉框。 选择哪种控件只看有没有这个元数据。
  • 下拉列表是空的，而且没有任何报错。 只有 "ClassName.FuncName" 这种外部静态函数的写法，在找不到函数时才会触发 ensure。
  • 受影响的只有这一个字段，其他属性照常显示。

这是一类典型的"编译期不报错、运行时悄悄失效"的反射陷阱。

10. 变量改名之后：Guid 找回机制

10.1 问题：绑定存的是名字

BoundName 是一个 FName，比如 "FOV"。如果策划把蓝图变量改名为 TargetFOV，FindFProperty("FOV") 就找不到了，绑定随之失效。

解决办法要借助蓝图本身的机制：蓝图里的每个变量都有一个不会随改名而变化的 FGuid。 UE 提供了两个函数，用于在名字和 Guid 之间互相转换：

  • UBlueprint::GetFieldNameFromClassByGuid：由 Guid 得到当前名字
  • UBlueprint::GetGuidFromClassByFieldName：由名字得到 Guid

所以可以在 Ref 里额外存一份 Guid：

1

3

#if WITH_EDITORONLY_DATA
	UPROPERTY()
	FGuid BoundGuid;      // 只在编辑器中存在，用于改名后找回

10.2 为什么运行时不能直接用 Guid

名字与 Guid 的对应关系，保存在 UBlueprint 的变量描述里，也就是 NewVariables 数组，其中每一项都带有 VarGuid。而 UBlueprint 是只在编辑器中存在的资产对象，Cook 时会被剥离，打包数据里只保留它生成的 BP_MyRig_C 类。

所以在打包后的游戏里，不仅 Ref 上没有 Guid（它被 WITH_EDITORONLY_DATA 包住了），连用来查 Guid 的对照表都不存在。名字是唯一能带进打包版本的线索。这就引出了一个硬性要求：

资产在保存或 Cook 之前，必须先把名字修正好。

10.4 为什么需要两种"为准"

关键要看在那个时刻，哪一个是最新的事实。

假设在细节面板里编辑之后，也以 Guid 为准。现在策划在下拉框里把绑定从 A 换成 B：

策划在下拉框选 B：   Name = B, Guid = GA   ← 细节面板只改了名字

10.5 挂到引擎的生命周期钩子上

钩子 参数 作用
PostLoad（在编辑器中加载时） false，以 Guid 为准 资产未打开期间变量可能被改过名，加载时修正名字

容易踩的坑：编译器都不会提醒你

遗漏或错误 现象
选项函数没写 UFUNCTION() 下拉框为空，而且没有任何报错
没有 override GetBoundName 如果基类返回 NAME_None，就永远找不到变量，每个 Ref 对每个类都会打一次 Warning
没有 override SetBoundName 如果基类实现是空函数，变量改名后名字不会跟着更新，保存后绑定就断了
把 Ref 放进 TArray 或嵌套的结构体里 运行时能用，但改名找回和数据校验会漏掉它
C++ 端用的是 FVector3f 它和蓝图的 FVector 是不同的 UScriptStruct，类型匹配会失败
AcceptsType 里没比较 Struct FRotator 等结构体也能被绑定上，读取时会把错误的内存当作 FVector 来解释

验证步骤

  1. 编译编辑器 Target。
  2. 在 Rig 蓝图中添加一个 Vector 变量，确认它出现在下拉框中，而 Float、Rotator 等变量不会出现。
  3. 给这个变量改名并保存，重新打开后，确认绑定的名字已经跟着更新。
  4. 删除这个变量，运行数据校验，确认会报 Error。
  5. 进入 PIE，确认日志中只出现一次 Warning，并且节点不修改相机。

12. 总结

回顾整条知识链：

  1. C++ 编译后名字就消失了，所以需要一张运行时的"名字 → 类型 + 偏移"表。在 UE 中，这张表就是 UStruct（包括 UClass、UScriptStruct、UFunction），表里的每一行是一个 FProperty。
  2. C++ 属性的表项由 UHT 生成，在模块加载时创建；蓝图变量的表项由蓝图编译器创建，登记在 BlueprintGeneratedClass 自己的表里，内存接在父类之后。打包后，这些表项从资产中反序列化得到。
  3. 类型由 FProperty 的子类表示，用 CastField 判断；结构体还要额外比较 Struct 指针。读取时使用 GetPropertyValue_InContainer 或 ContainerPtrToValuePtr；属性标记决定了哪些变量允许被绑定。
  4. Container 是"装着这个属性的那个对象"的地址。 属性在哪张表里找到，就传那张表的实例地址；多层嵌套时逐层往下传。
  5. 运行时以类为 key 做缓存。 TWeakObjectPtr 防止类被销毁后误判命中；FieldPathSerialNumber 应对编辑器重新编译时 FProperty 被重建的情况；查找失败的结果也会被缓存，避免重复查找和日志刷屏。
  6. 编辑器一侧：Node 通过反射遍历自己身上的 Ref；GetOptions 通过反射调用 UFUNCTION 来生成下拉选项，过滤规则与运行时保持一致；Guid 负责在变量改名后找回绑定；PostLoad、PreSave、PostEditChangeProperty、IsDataValid 各自在合适的时机完成修正与校验。

理解了这些之后，再去看 UE 里任何"按名字操作属性"的代码，比如细节面板、序列化、属性路径、蓝图节点的 Get/Set，你会发现它们底层都是同一套机制：找到表，找到行，确认类型，再用正确的 Container 加上偏移。
